# 鼻部习惯检测器

一个完全本地的工具，把"不自觉摸/抠鼻子"这个无意识动作变成**看得见的数字**。

- 摄像头画面**只在内存里处理**，不录制、不上传、不落盘
- 模型和 wasm 全部本地化，**断网可用**
- 两种用法：书桌前用摄像头自动检测，离开书桌用手机随机打卡（通知可镜像震到 Apple Watch）

---

## 一、第一次使用（三步）

### 1. 离线资源（已经替你下好了）

`vendor\` 里已经有全部 7 个文件（共 29.4MB：wasm + 手部模型 + 面部模型），**这一步可以跳过**，直接看第 2 步。

只有当 `vendor\` 被删了/拷到别的电脑上却是空的，才需要重新下（需联网一次）：

右键 `download-assets.ps1` → **使用 PowerShell 运行**。或者在本目录打开 PowerShell：

```powershell
powershell -ExecutionPolicy Bypass -File .\download-assets.ps1
```

下载完就永久离线可用了。

### 2. 启动

双击 **`start.bat`**。会弹出一个命令行窗口 + 自动打开浏览器（`http://127.0.0.1:8787`）。

> 为什么不能直接双击 `index.html`：浏览器只允许 `127.0.0.1` / `localhost` / https 访问摄像头，`file://` 会被直接拒绝。`start.bat` 就是在本地起一个只监听 127.0.0.1 的静态服务，不对外网开放，不需要管理员权限。

### 3. 点"启动检测"，允许摄像头

状态变成 **哨兵中** 就开始工作了。摸一下鼻子试试，屏幕边框会闪一下、计数 +1。

用完直接关掉那个命令行窗口即可。

## 二、它是怎么判定的

每帧同时跑两个 MediaPipe 模型：

| 模型 | 作用 | 频率 |
|---|---|---|
| FaceLandmarker（478 点） | 定位鼻尖、两侧鼻翼、鼻孔下缘，围成"鼻区多边形" | 每 2–4 秒一次，然后缓存 |
| HandLandmarker（21 点） | 定位食指/中指指尖 | 5fps 起，手进画面时自动加速 |

**判定规则**：指尖落入鼻区多边形（向外扩大 1.2 倍以覆盖按压时的形变）并**连续停留 ≥ 0.8 秒** → 记 1 次。

**"一次"的定义**（状态机，不是逐帧计数）：

```
手进入鼻区 ──≥0.8s──> 记 1 次，开始计时
   │                        │
   └── 离开 <5s 又回来 ─────┘   ← 还是同一段，不重复计数
                            │
                       离开 >5s ──> 这段结束，时长入账
```

所以**摸着不放一分钟 = 1 次 + 60 秒时长**，这正是长动作该有的记法。你要盯的核心指标其实是**总时长**，不是次数。

**分阶段提醒**：
- 0.8 秒 → 蓝色边框闪一下（记数）
- 超过 10 秒 → 橙色边框闪两下 + 一句话（这是唯一能在动作"中途"打断你的时机）

### 参数怎么调

| 参数 | 默认 | 什么时候改 |
|---|---|---|
| 记数阈值 | 800ms | 误报多就调大（1200–1500）；动作太快抓不到就调小（500） |
| 结束间隔 | 5000ms | 你习惯断断续续摸（摸一下放一下）就把这个调小到 2000，否则会被算成一段 |
| 长动作提醒 | 10000ms | 想更早被提醒就调小 |
| 鼻区扩大 | 1.2 倍 | **误报主要集中在脸/下巴/额头**时调小到 1.0；漏报（明明摸了没记）调大到 1.4 |

调试技巧：勾上 **"调试标注"**，预览画面上会画出蓝色鼻区多边形和红/绿指尖圆点。绿色 = 判定为触摸。**先看一眼这个多边形有没有正好框住你的鼻子**，这是调参的唯一正确入口。

## 三、功耗：真实情况

耗电大头**不是摄像头**（传感器恒定约 0.5–1.5W），是每帧跑模型。所以设计上是这么省的：

1. **分级唤醒**：平时只跑手部单模型（5fps），手抬进画面才加速到 ~11fps
2. **面部低频缓存**：你的脸相对摄像头几乎不动，鼻区多边形每 2.5 秒才重算一次，不必每帧跑 478 点
3. **三档强度**：省电（2fps）/ 平衡（5fps，默认）/ 灵敏（10fps）
4. **前台闲置就停**：页面在前台且键鼠 5 分钟没动 → 关摄像头，动一下自动恢复（可关）
5. **离开电脑就停**（默认关）：用 Windows 的 `GetLastInputInfo` 看**整台机器**的键鼠，闲置 10 分钟 → 关摄像头；切到别的窗口后也能生效
6. **没人在就降省电档**（默认开）：镜头里连续 2 分钟没检测到人脸 → 自动降到省电档（2fps），有人回来立刻恢复原档。**降档而不是停**，否则你回来时它已经关了而你根本不知道
7. **暂停 30 分钟**：开会、见人用

> 注意：**切走标签页默认不关摄像头**（你想让它后台继续盯着），见下面「三之二」的实测数字。想恢复旧行为，把参数里的「切到别的窗口也继续」取消勾选即可。
>
> 这条曾经是个 bug：最早那版用「本页面收到的键鼠事件」算闲置，而页面切到后台后一个事件都收不到，于是“切走干活”被当成“人走了”，五分钟准时把摄像头关了。现在闲置只在前台算（后台要停请显式勾「离开电脑就停」）。

页面右下角 **"功耗自检"** 面板给的是实测值，不是估算：

- **占用(单核)** = 累计推理耗时 ÷ 累计运行时长。这个数字就是真实成本
- **摄像头开启** = 累计开着多久

**我这台机器上的实测**（Intel UHD Graphics 620 集显、Chrome、GPU delegate，`test/smoke.html` 量的）：

| 指标 | 实测 |
|---|---|
| 手部单帧（稳定后中位） | 19.8–25.6 ms |
| 面部单帧（稳定后中位） | 11.9–25.6 ms |
| 平衡档（哨兵 5fps + 面部 0.4 次/s） | **实测 13.6–14.9% 单核** |
| 省电档 / 灵敏档 | 约 6% / 约 26%（按同一单帧耗时推算） |

> 注意两个坑：① 第一次推理要编译着色器，实测 0.4–2.5 秒（远大于稳定后的 20ms），所以启动时状态会先显示"预热模型…"，这一下正好把它吃掉，不会让第一帧误判或拖慢；② 跑在 GPU delegate 上，所以"占用"是**主线程被占用**的时间（含 GPU 提交等待），不等于 CPU 满载。

**以你自己面板上的数字为准**——不同 CPU/显卡差很多。如果觉得贵，切"省电"档，或者把"离开电脑就停"打开。

> 为什么不干脆"定时抓拍"？抓拍必须让摄像头 stream 一直开着（窗口只是抽帧），省不掉传感器；真要 `stop()` 再开，唤醒延迟 0.5–2 秒正好漏掉动作。而且摸鼻子一摸就是十几秒以上，抽样看起来够用，但"开始摸的那 1 秒"经常正好落在两次抽帧之间——而边界点才是你真正需要察觉的瞬间。

## 三之二、切到别的窗口还能不能检测？

**能，但取决于你怎么打开它。** 原来那版是切走就 `stop()`，所以摄像头会关——现在改了：主循环不再用 `requestAnimationFrame`（标签页不可见时浏览器会直接暂停它），改成定时器驱动，切走继续跑。

剩下唯一的敌人是浏览器的"后台节流"：隐藏页的定时器被限到 1 次/秒，藏久了还可能降到 1 次/分钟。所以：

| 打开方式 | 后台推理帧率 | 能不能抓到 |
|---|---|---|
| `start.bat` 打开的**专用窗口** | **实测 4.92 帧/秒**（和专业级 5fps 档完全一样） | 能，等于前台 |
| 自己用普通 Chrome 打开同一地址 | **实测 1.00 帧/秒** | 摸 2 秒以上能抓，1 秒内的会漏 |
| 把「切到别的窗口也继续」关掉 | 0（摄像头直接关） | 不能，但省电 |

实测环境：`start.bat` 的专用窗口带 `--disable-background-timer-throttling --disable-backgrounding-occluded-windows --disable-renderer-backgrounding`，12 秒隐藏期间跑了 59 次手部推理（≈4.9 次/秒）、5 次面部推理（面部本来就是 2.5 秒一次），`video.currentTime` 正常前进 12.01 秒（说明摄像头流没断）。对照组（不带这些参数）同期只有 12 次手部推理，正好 1 次/秒。

两点要知道：

- 专用窗口用的是**独立配置目录** `%LOCALAPPDATA%\NoseHabit\chrome-profile`（参数对已经开着的 Chrome 无效，只能用独立实例）。所以**统计数据的 localStorage 绑在这个专用窗口上**——你用别的 Chrome 打开同一地址，数据是分开的两份。平时就用 `start.bat` 打开，别混着用。
- 万一副本被限速，页面状态栏会直接写出来（"后台被限速 0.4fps"）并弹一次提示，不会让你以为在检测、其实已经死了。这个判断是拿实际循环次数算的，不是猜的。

### 自己把自己关掉的那个 bug（已修）

后台能继续跑之后，又冒出另一个问题：**在后台挂几分钟，摄像头自己就关了**。

原因不是浏览器，是我自己写的省电逻辑：那时用"本页面最后一次收到键鼠事件"算闲置，而页面一旦切到后台，**一个 `mousemove` 都收不到** → "切走干活"被当成了"人离开电脑" → 5 分钟准时 `stop()`。

现在的规则：

| 场景 | 会不会关摄像头 |
|---|---|
| 切到别的窗口，一直在用电脑 | 不会（闲置只在前台算） |
| 切到别的窗口，人也走了 | 只有当你自己勾了「离开电脑就停」才会（默认关） |
| 页面在前台，5 分钟没碰键鼠 | 会（"前台闲置就停"，默认开） |
| 镜头里 2 分钟没人 | 不会，只降到省电档 |

「离开电脑就停」看的是**整台机器**的输入，用 Windows 的 `GetLastInputInfo`（走本机服务 `GET /api/idle`，返回 `{ok,idleMs}`）。

> 一个实测发现：**这台机器上它基本永远返回 0**。我以 500ms 间隔采样 16 次，系统闲置时长最大值只有 844ms——也就是说几乎每半秒就有一个输入事件（这台机器装了 Logitech Options+ / LogiBolt，很可能是它在报事件，也可能是无线鼠标的微小抖动）。所以这个开关在这台机器上可能永远不会触发，我把它做成了**默认关**、不依赖它。真要靠它省电，先自己去 `/api/idle` 看一眼数字会不会涨。

## 三之三、微信 / 手机提醒

**能做，但得先说清楚：微信没有给个人开放的消息接口。** 能"推到微信"的都是第三方中转，三选一（都在页面「微信 / 手机提醒」卡片里）：

| 通道 | 怎么拿 key | 免费 | 备注 |
|---|---|---|---|
| Server酱 | sct.ftqq.com 微信扫码登录 | 每天有额度 | 消息进"服务通知"，最快 |
| PushPlus | pushplus.plus 微信扫码登录 | 有免费额度 | 同上 |
| 企业微信群机器人 | 企业微信群 → 添加机器人 → 复制 webhook | 不限 | 需要有企业微信群；个人也能注册企业微信 |
| 自定义 webhook | 你自己的地址 | — | 能收 POST JSON 的任何东西（自建、n8n、Home Assistant…） |

配置：选通道 → 粘贴 key → 勾「启用」→ 点「发测试」，成功会显示 `已发出（HTTP 200）`。触发点三个独立开关：长时间提醒（默认开，30 秒内不重复推）、每次记数、打卡时。

**为什么不让浏览器直接 POST 那些接口？** 企业微信/Server酱/PushPlus 的响应都没给 `Access-Control-Allow-Origin`，浏览器跨域 POST 会被 CORS 拦掉。所以改成走本机服务转发：页面 → `POST http://127.0.0.1:8787/api/notify` → 本地服务代发。这样 key 只在你自己机器上，也不需要在浏览器里开任何奇怪的权限。

**离线怎么办？** 关掉「启用」就是纯离线，一个包都不发。这也是提醒一个真实的取舍：开着微信提醒就必须联网，而且**推送会经过第三方服务器**（消息内容是"手在鼻子那儿已经 32s"这类，不含画面）。

## 三之四、系统提醒（不用盯着这个页面）

页面内弹的提示、闪的边框，只在你看着这个窗口时有用。要让提醒在你用别的软件时也出现，有两条路：

### 为什么不用浏览器自带的通知

页面里调 `new Notification()` 本来是最省事的（Chrome 在后台也会走 Windows 通知中心），**但这台机器上用不了**：

```
HKCU\Software\Microsoft\Windows\CurrentVersion\Notifications\Settings\Chrome
  Enabled = 0
```

Chrome 的通知在系统层是关着的。这种情况下 `new Notification()` 不报错、`permission` 也是 `granted`，但通知被系统静默丢掉 —— 代码以为发出去了，你永远看不到。这种“以为成了其实没成”的坑比直接报错更糟，所以不走它。

### 走法：页面 → 本机服务 → Windows 通知中心

```
页面 app.js  --POST /api/toast-->  start.ps1  --WinRT-->  Windows 通知中心（右下角弹窗）
             --POST /api/voice-->  start.ps1  --SAPI-->   扬声器念一句
```

- **不需要装任何东西**（不用 BurntToast 模块，PS 5.1 直接调 WinRT 的类型投影就行）
- **不需要网页通知权限**，也不受 Chrome 通知开关影响
- 走的是 `powershell.exe` 的通知身份，所以通知来源名称会显示成“Windows PowerShell”；换成自己的名字需要注册开始菜单快捷方式（要做的话在 `start.ps1` 里加约 30 行互操作代码，现在不值当）
- 语音优先挑中文音色（本机是 `Microsoft Huihui Desktop`），用 `SpeakAsync` 不阻塞服务器，合成器只建一次

接口（都在本机，`GET` 一律 405，JSON 坏了返回 400）：

| 接口 | 请求体 | 说明 |
|---|---|---|
| `POST /api/toast` | `{title, text, scenario}` | `scenario` 可选 `default/reminder/urgent/…`，`urgent` 会停留更久 |
| `POST /api/voice` | `{text, rate, volume}` | `rate` -10…10，`volume` 0…100 |

### 提醒分级（做了才知道为什么要分）

如果每个事件都弹窗都会叫，结果一定是你把通知关了。所以：

| 事件 | 页面看得见时 | 切到别的窗口时 |
|---|---|---|
| 记数（刚进鼻区 ≥0.8s） | 边框蓝色轻闪 + 一声提示音 | 不打扰（这是正反馈，不是告警） |
| 摸着不放 ≥「长时间提醒」 | 橙色闪两下 + 页内气泡 | **系统通知（带提示音）+ 语音“手放下吧”** |
| 还不放 ≥30s（或阈值的 3 倍） | 橙色闪 | 再来一条通知 + 语音“还在摸鼻子，把手拿开”——**只催这一次** |
| 离开电脑（勾了微信推送） | 手机提醒 | 同 |

每级都只在进入该级的那一瞬间触发一次，不会反复叫；`toastOn` / `voiceOn` 两个开关关掉后一个请求都不会发（下面有测）。

## 四、手机端（随身打卡）

同一个页面，切到 **"随身打卡"** 标签：

- 随机间隔（默认 20–50 分钟）弹出"手现在在哪？"
- 点【在脸上】/【不在】，记录进同一份本地数据，统计里一起算

### iPhone 添加主屏幕

Safari 打开 `http://<电脑局域网IP>:8787` → 分享 → 添加到主屏幕。
（电脑要在同一 Wi-Fi 下，且**别关 start.bat 那个窗口**。手机访问局域网 http 只能用打卡功能，摄像头需要 https，所以手机端不做摄像头检测。）

### 关掉页面时怎么办：用「快捷指令」兜底

iOS 不允许网页在关闭后自己定时弹通知。用系统自带的自动化补上，而且通知会**镜像震到 Apple Watch**：

1. iPhone 打开 **快捷指令 → 自动化 → 新建自动化**
2. 选 **特定时间** → 时间设为你想被提醒的点（比如 10:00、14:30、16:00、21:00），重复选 **每天**，勾 **立即运行**
3. 添加操作 **显示通知**，内容写：`手现在在哪？`
4. 保存。多建几个不同时间点就是"多次随机提醒"

> Apple Watch 上没有独立 app：真正的 watchOS 应用需要 macOS + Xcode 才能编译安装，Windows 上做不出来。但上面的通知会自动镜像到手表并震动，效果上够用——而且震动比弹窗好，因为低头看手机本身也可能是触发动作。

## 五、隐私

- 摄像头帧只在浏览器内存里 → MediaPipe 模型 → 丢弃。**没有任何帧被保存**
- 没有网络请求（下载资源那一次除外），断网后功能完全正常，可以自己验证：断网 → 刷新 → 照样能检测
- 数据只写在本浏览器的 `localStorage`（key: `noseHabit.v1`），不上传
- 服务只监听 `127.0.0.1`，局域网外的机器访问不到（手机端要用时才会被同 Wi-Fi 设备访问）

## 七、已知限制（不糊弄）

1. **无法区分"摸"和"抠"**。手指被鼻子遮挡时，2D 关键点判断不了"进没进去"。软件只统计"手到鼻部区域"——但这已经足以让无意识动作变可见。
2. **只有对着摄像头时有效**。书桌场景覆盖好，躺床上、走路时完全无效，靠打卡兜底。
3. **会把"托腮压到鼻子附近""揉眼睛时手背扫过鼻梁"算进去**。用调试标注看多边形，必要时把"鼻区扩大"调到 1.0–1.1。
4. **强逆光 / 摄像头离脸太远**（脸宽小于画面 1/8）时定位会掉，表现为 `面部单帧` 有值但完全不记数 → 靠近一点或调亮。
5. 手机端只有打卡，没有摄像头检测（需要 https 部署，且角度不现实）。

## 八、常见问题

| 现象 | 处理 |
|---|---|
| 点启动提示"权限被拒绝" | 地址栏左侧锁图标 → 摄像头 → 允许 → 刷新 |
| 提示"摄像头被占用" | 关掉会议软件 / 相机 App，或设备管理器里禁用再启用摄像头 |
| 状态一直"加载模型…" | 检查 `vendor\` 里 7 个文件是否齐全；控制台（F12）会显示具体哪个 404 |
| 完全不记数 | 勾"调试标注"看鼻区多边形是否框住鼻子；看 `面部单帧` 是否有数字 |
| 误报太多 | 调大记数阈值 → 调小鼻区扩大 → 切"灵敏"档提高判定密度（反而更准） |
| 风扇狂转 | 切"省电"档 + 勾"离开电脑就停" |
| 端口 8787 被占 | `start.bat 8899` 换端口 |

## 九、文件说明

```
nose-habit\
  start.bat                双击启动（可传端口：start.bat 8899）
  start.ps1                本地静态服务器（TcpListener，只监听 127.0.0.1，无需管理员）
  download-assets.ps1      一次性下载离线资源
  index.html               界面
  app.js                   检测 / 判定 / 统计 / 打卡
  vendor\                  wasm + 两个模型（已下好，共约 29MB）
  test\
    debug-nose.html        鼻区多边形标定页（选一张本地照片，验证点位）
    smoke.html             性能冒烟测试（不用摄像头，量单帧耗时和 GPU 型号）
  README.md
```

想验证鼻区点位准不准：启动后访问 `http://127.0.0.1:8787/test/debug-nose.html`，点「选择文件」挑一张你自己的正脸照片（只在本地解码，不上传），它会把 478 点里的鼻部点位和多边形画在照片上 —— 这个蓝框就是检测器判定你“手在鼻子附近”的区域。

想看你这台机器跑这两个模型到底多贵：访问 `http://127.0.0.1:8787/test/smoke.html`，它会打印 GPU 型号、手部/面部单帧耗时中位数，以及换算出的单核占用。

## 十、这版做过哪些验证

写完之后我用 Chrome 无头模式 + 模拟摄像头把主要链路跑了一遍（不是"看着代码觉得对"）：

| 项目 | 结果 |
|---|---|
| 两个模型加载 + 推理 | 通过，GPU delegate 成功，零报错 |
| 鼻区多边形是否真的框住鼻子 | 通过（照片上肉眼确认，框住鼻梁到鼻头） |
| 连续摸 1.5s | 记 1 次（不是 15 次），实时计时 1.5s |
| 长动作提醒 | 到阈值触发，只触发一次 |
| 再摸 1.5s | 正好第 2 次 |
| 只碰 0.1s | 不记 |
| 摸 0.2s / 松 0.4s / 再摸 0.2s | 算同一段，累计过阈值才记 1 次 |
| 离开超过结束间隔再摸 | 记为新的一段 |
| 刷新页面后 | 次数和时长都还在（localStorage） |
| 导出 CSV / JSON | 格式正确，CSV 带 BOM（Excel 打开不乱码） |
| 打卡 / 切换标签页 / 统计图 | 正常 |
| 切到另一个标签页（专用窗口带关限速参数） | 后台仍 4.92 帧/秒，手部推理 59 次/12 秒，摄像头流不断 |
| 同上但不带参数（对照） | 降到 1.00 帧/秒，正好是浏览器的后台节流上限 |
| 微信提醒链路 | 用一个本地假 webhook 当接收端，页面点「发测试」→ 本机服务代发 → 假接收端收到 UTF-8 中文完整无乱码，状态显示“已发出（HTTP 200）”；打到不存在的端口时正确报错 |
| 后台检测开关 | 默认开，点掉即关并写入设置，关掉后再切走会立即 stop() |
| **后台常驻会不会自己关摄像头**（回归） | 伪装成 hidden + 页内闲置 9 分钟：仍然 `running=true`、`by=null`、状态显示“后台检测中”——**不再自动关** |
| 前台闲置该停还是要停 | 页内闲置 6 分钟 → `running=false`、`by='idle'`、状态“闲置暂停”；派一个 mousemove → 3 秒内自己 start() 回来 |
| 「离开电脑就停」（整机键鼠） | 注入 11 分钟系统闲置 → 停，`by='away'`；闲置归零 → 自动恢复 |
| 「没人在就降省电档」 | 注入“2.5 分钟没看到脸” → `effTier` 从 balance 变 saver、状态“镜头里没人 · 省电档”、**摄像头没停**；人脸恢复后回到 balance |
| 判定逻辑没被这次改动带坏 | 摸 1.5s → 记 1 次（d=1.4s）；再摸 1.2s → 2 次；只碰 0.1s → 仍是 2 次 |
| `/api/idle` | `{"ok":true,"idleMs":31}`，POST → 405 |
| 系统通知 `/api/toast` → Windows 通知中心 | 通过。发了两条测试通知，且注册表 `…\Notifications\Settings\{1AC14E77-…}\…\powershell.exe` 的 `LastNotificationAddedTime` 确实往前跳了（= 通知平台真的收了，不是静默吞掉） |
| 语音 `/api/voice` → SAPI | 通过，本机音色列表里有 `Microsoft Huihui Desktop`，`SpeakAsync` 立刻返回（HTTP 200 用了 512ms，含首次建合成器） |
| 两级提醒节流 | 用 `__nose` 驱动连续 32 秒的“摸”：`longWarn=2000` 下总共只发了 4 个请求（第 2s 一组通知+语音、第 30s 再一组），**每级各一次**，没有重复轰炸 |
| 两个开关真能关 | `toastOn/voiceOn` 都设 false 后再驱动一段，新增 `/api` 请求数 = **0** |
| 「试一下」按钮 | 点一下 → `/api/toast` + `/api/voice` 各一次，状态变绿显示“通知已发出；语音已播放” |

**没验证的**：① 真实摄像头下的判定准确率——这个必须在你的书桌前、你的光线下、你的姿势下才能量，第一次用请先勾上"调试标注"，看那个蓝色多边形有没有正好框住你的鼻子，再看打字 10 分钟会不会误报，然后按第二节的表调参数；② 真的微信推送（没你的 key 发不出去，链路已用假 webhook 验到底）。
